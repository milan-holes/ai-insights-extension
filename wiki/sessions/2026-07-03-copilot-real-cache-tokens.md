# Session: Copilot real cache tokens + transcripts/ discovery - 2026-07-03

## What was done

- Audited `src/providers/copilot.ts` for whether a better GitHub Copilot cache-token source exists than the estimate it was using.
- Found that Copilot's own `debug-logs/{sessionId}/main.jsonl` telemetry carries real `cachedTokens` — directly contradicting our own 2026-07-02 wiki finding that cache data was "confirmed unavailable." Added `extractCachedTokensFromDebugLog()` to read it.
- Verified on this machine: our discovery code (`addSessionFilesFromDir`) only reads files directly inside `debug-logs/`, never descending into the `{sessionId}/` subfolders where `main.jsonl` actually lives. The 2026-07-02 investigation made the same non-recursive mistake by hand. Real `llm_request` events with `attrs.{inputTokens,outputTokens,cachedTokens,model}` were sitting there the whole time.
- Also found Copilot Chat has moved (confirmed `copilotVersion: 0.55.0`, 2026-07-02 session on this machine) to a new `transcripts/{sessionId}.jsonl` typed-event format that our discovery never scanned at all — meaning current-version Copilot sessions were entirely invisible, not just poorly cache-estimated.
- Implemented: `transcripts/` discovery, a new parser for its event schema, and a shared `attachRealCacheData()`/`readDebugLogEvents()` pair that correlates real per-call telemetry from `debug-logs/{sessionId}/main.jsonl` back onto interactions for *all* session formats (JSON, delta-jsonl, and the new transcripts format), falling back to the existing heuristic only when no debug log is found.
- Verified end-to-end against real local session files (compiled to `out/`, parsed all 85 discovered files with zero errors); one real session showed `inputTokens: 103166` / `cachedTokens: 76288` (74% hit rate) flowing through as real, non-estimated data.
- Follow-up: audited every field in `transcripts/*.jsonl` for anything else useful. Found `assistant.message.toolRequests[].arguments` (the model's own generated tool-call payload - full `apply_patch` diffs, `create_file` bodies, terminal commands) was being silently dropped from the fallback text-estimate; wired it in (one session's fallback output estimate went 824 → 7,386 tokens). Tool *results* aren't recoverable at all from this format (`tool.execution_complete` only carries `{toolCallId, success}`). Also found `debug-logs/{sessionId}/models.json` (a snapshot of GitHub's model catalog: billing multiplier, context window limits) sitting unused next to `main.jsonl` - it's billing/limit metadata, not usage data, so left unwired for now.
- Follow-up: measured how often real telemetry actually shows up. Across 41 real sessions on this machine, only **1** had any `llm_request` data - every other `debug-logs` folder was a one-line stub. Initially attributed this to agent-mode vs. ask-mode (the one populated session was agent-mode). **Corrected after the user pointed out they'd just enabled `github.copilot.chat.agentDebugLog.fileLogging.enabled`**: `settings.json` mtime (2026-07-02 22:49-22:59) lines up almost to the minute with the one populated session's start time (22:55:26), and every stub-only debug log predates that edit. The "agent-mode-only" theory was an overreach from n=1 that coincided with the setting flip, not a confirmed pattern - retracted. What's confirmed: the setting is opt-in and off by default, so most Copilot users get no debug-log data at all. Conclusion: the heuristic fallback (`applyCacheHeuristic`) remains the primary mechanism for the vast majority of Copilot users, since most won't have this setting on.
- Follow-up: since the gap is "most users never enable this setting" rather than "the data doesn't exist," the user asked to have AI Insights turn it on for them and document it in the README. Implemented a one-time activation prompt (`maybePromptEnableCopilotDebugLogging` in `extension.ts`) with explicit **Enable / Not now / Don't ask again** choices - never flips the Copilot setting silently, since doing so makes Copilot write full prompt/code content to local debug-log files, a real data-handling change worth surfacing, not just a number-accuracy toggle. Added a matching command (`aiInsights.enableCopilotRealCacheData` / "AI Insights: Enable GitHub Copilot Real Cache Data") to re-trigger it later, and a setting (`aiInsights.providers.copilot.promptToEnableRealCacheData`, default `true`) to turn the automatic prompt off. Rewrote the README's old "No GitHub Copilot cache tracking" limitation into a new "GitHub Copilot: Real Cache/Token Data" section reflecting the corrected reality: real when the setting is on, calculated otherwise.

## Decisions made

- Correlate debug-log events to interactions by **timestamp bucketing** (assign each `llm_request` event to the most recently-started interaction), not by ID — the debug log and session files share no request/message ID, and turn IDs in the transcript format aren't 1:1 with actual LLM calls (agent loops can make several calls per turn, or a turn can make zero).
- `cachedTokens` from the debug log is treated as a subset of `inputTokens` (`inclusive` semantics, matching OpenAI's `cached_tokens` field which Copilot's OpenAI-style backend models forward directly) with `cacheWriteTokens` always `0` — OpenAI-style caching is automatic and doesn't report or bill writes separately, unlike Anthropic.
- `attachRealCacheData()` is wired into all three existing parse paths (JSON, delta-jsonl) in addition to the new transcript parser, not just the new format — real telemetry should win over the heuristic wherever it exists, regardless of which session format surfaced the interaction.
- Kept the existing heuristic (`applyCacheHeuristic`) completely intact as a fallback for sessions/interactions without a matching debug log, rather than replacing it — debug logging isn't guaranteed to be present or retained for every session.
- For auto-enabling the Copilot setting: asked the user to choose between silent auto-enable, a one-time consent prompt, or manual-only (command + docs). Chose **one-time prompt with consent** — enabling `agentDebugLog.fileLogging` makes Copilot persist full prompt/code content to local debug-log files, which is a real data-handling change for a setting this extension doesn't own, not just an accuracy toggle; silently flipping it for every install felt wrong for a change with that shape, even though it's easy to reverse. Never re-prompts once resolved (`Enable` or `Don't ask again`), and `Not now` leaves it unresolved so it's offered again next activation rather than never again.

## Follow-up / known gaps

- Debug-log retention is unknown (not investigated) - if VS Code prunes old `debug-logs/{sessionId}/` folders more aggressively than `chatSessions`/`transcripts`, older sessions will silently fall back to the heuristic, which is by design but worth knowing.
- No unit tests exist for `copilot.ts` in this repo (verified manually against real local data instead, per this session's testing). Adding fixture-based tests for `parseCopilotChatTranscriptSession` and `attachRealCacheData` would be worthwhile follow-up.
- The 2026-05-01 Copilot parsing-precision research notes predate this finding and weren't updated - they're a historical snapshot, not corrected in place.
- The activation prompt was verified by typecheck only (`tsc --noEmit`), not by actually running the extension host and clicking through the notification - no way to drive VS Code's UI from this environment. Worth a manual smoke test (`F5` / Extension Development Host) before shipping: confirm the prompt appears when the Copilot setting is off, `Enable` actually flips it and persists across reload, and `Don't ask again` / re-running the command behave as described.
- Still unconfirmed whether ask/chat-mode Copilot sessions populate full `llm_request` telemetry once the setting is on, or only agent-mode ones (see the retracted claim above) - worth checking once more real post-enablement sessions accumulate.
